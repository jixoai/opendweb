> 源头：Owner 2026-09-24 思维原型（原话逐字存档，编号 [W0]-[W6]）。
> 本 change 的裁决信源与 home-hub [H0]-[H8] 同级；实现期出现的新裁决追加 [W7]+。

## Owner 原话存档（逐字）

### [W0] 出发点与 SMB 的取舍

> 我们不是在 dweb 里面内置了 HTTP 的传输协议吗？ 我在想能不能把 SMB 协议也内置了？
> 我换个说法，smb 也许不需要，但我想去内置一个简单的跨设备同步和共享能力：
> 其中就包括端口共享、文件夹共享、文件夹同步。

**裁决**：SMB 协议本身不内置；内置的是「简单的跨设备同步和共享能力」三件套
（端口共享/文件夹共享/文件夹同步），可借道 dweb 已有的 HTTP 传输。

### [W1] 端口共享语义

> 端口共享这个很好理解：A 设备有 8080 端口服务，我把它映射到我 B 设备的 9090 端口上，
> 这样我在 B 设备上访问 9090 等同于直接访问 A 设备的 8080。

### [W2] 文件夹共享形态（webui 提供简单 FS 操作）

> 文件夹共享则是类似 smb 协议，或者我们可以在 webui 基于 smb 协议实现原生文件系统的
> 操作。当然如果是 smb 协议的话可能会更原生，不过用户可能不懂如何对接 smb 协议，
> 所以 webui 这里可以提供简单的文件系统操作的能力。

**裁决**：不要求 SMB wire；对用户的呈现是 webui 里简单的文件系统操作能力。

### [W3] 文件同步 = 虚拟 git（单向/双向/冲突）

> 文件同步则是另外一种技术的，涉及到多设备协同的能力，可以考虑构建一个虚拟的 git
> 仓库（使用 js 技术或者 go 技术，这是可以内置的），然后基于这种技术，实现同步，
> 同步有两种模式：单向同步和双向同步。
> 像文件夹共享本身就属于简单意义上的单向（有明确的 C/S 概念），在加上自动下载，
> 就实现了单向同步。也就是说 A 设备上修改了这个文件或者文件夹里的内容，那么 B 设备
> 就会收到这个变更并跟随变更。就像 A 做了 push。然后 B 做 pull。
> 而双向同步意味着，A/B 都可以做 push（如果冲突则自动 merge，如果无法自动 merge
> 就提醒警告用户来手动选中一个版本，当然如果能让 AI 自己来决策如何 merge 那其实
> 更好，或者我们可以直接把 git merge 冲突的内容展示出来，让用户自己手动处理这些
> 变更问题）。最终 A/B 自己再去做 push 直到不再冲突，然后再彼此 pull 来拉取更新。

**裁决要点**：
- 同步引擎=虚拟 git 仓库，JS 或 Go 技术内置（不依赖系统 git 二进制——待设计轮冻结具体选型）；
- 单向 = 共享 + 自动下载（服务侧 push 语义 / 客户侧 pull 跟随）；
- 双向 = 双方都可 push；冲突自动 merge；无法自动 merge 时提醒用户手动选版本；
  更好=AI 决策 merge，或直接展示 git merge 冲突内容让用户手动处理；处理完再
  push 直到不再冲突，然后彼此 pull。

### [W4] 动机（刚需，验收的真人场景）

> 这种文件同步的产品之前市面上应该存在过，我之所以提出要做这个，是因为这个现在
> 属于我的刚需，我有多台设备需要去同步 Agents-skills/prompt/wiki/configs 等等，
> 平时手动维护非常麻烦。

**验收锚点**：多设备同步 agents-skills/prompt/wiki/configs 是第一用户故事。

### [W5] webui 插件化（Cordis kernel 候选）

> 如果你觉得 webui 本身太重。那么 webui 可以自身进一步插件化，实现功能的拔插。
> 那么 webui 自身可以只专注于做 服务启动；设备发现、认证、互联、管理。
> 然后其余都用 webui 的插件系统来实现。这时候可以用 Cordis kernel 实现 webui
> 这套系统，这样 http 端口共享、文件共享、文件同步 等功能都可以用插件系统来做
> 进一步的安装和启用。

**裁决要点**：
- webui 核心=服务启动、设备发现、认证、互联、管理（拔插后核心只保留这些）；
- 其余能力全部走 webui 插件系统（安装/启用制）；
- Cordis kernel（@cordisjs/core）为实现候选——设计轮评估采纳与否。

### [W6] 插件生态愿景（非首发，面板占位）

> 由此一来，我们还可以开发更加复杂的插件，比如 vpn 插件：模拟一个虚拟网络，这可以
> 实现 tailscale 的技术。比如 clash 插件：将本机作为一个 clash 的网络节点共享给其它
> 节点。比如 AI 插件：我们之前开发过 ../../ai-fly 这个项目，将本机的 Codex 的订阅
> 服务或者 Claude 的订阅服务共享给局域网。比如 ssh 插件：实现远程终端连接的技术。
> 比如屏幕共享插件：实现远程协作。
>
> 目前 http 端口共享、文件共享、文件同步 这三个功能是第一批需要先做的，其它可以
> 晚一点（你可以在插件面板中提供一个"即将推出"的 flag）

**裁决**：首发=端口共享+文件夹共享+文件同步三件套；vpn/clash/AI(参考 ai-fly)/ssh/
屏幕共享为后续路线，插件面板以「即将推出」占位呈现。

## 走查含义（由裁决推导，待设计轮细化冻结）

1. 三件套均以**插件**形态交付（即使实现物理上在仓库内，产品面=可安装/可启用的插件）；
2. 端口共享/文件夹共享/文件同步的底层传输优先复用 dweb 既有 HTTP 传输面
   （fetchHttp/serveHttp，app-protocol-layer 已下沉 Rust + NAPI 绑定）；
3. 安全红线沿用既有基线：admin/成员凭证不出面（0600/不进浏览器 URL argv 日本 IPC）、
   路径白名单与逃逸防护、明文告知；文件同步落在用户目录时必须尊重既有数据
   （不碰 `~/.opendweb/nodes.json` 等用户数据）；
4. webui 三视角控制台/五行分流/接入卡片等 home-hub 既有面零回归（既有 webui 测试全绿）。
