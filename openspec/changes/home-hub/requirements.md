# home-hub：家庭中枢（Owner 需求存档）

> 本文件逐字存档 Owner 的产品输入与裁决，是本 change 不可挑战的依据。
> 工程面解读与设计决策见 design.md（引用裁决编号 [H1]…[H3]）。

## 初衷（2026-09-23，Owner）

> 我之所以提到这个，是因为很多情况下我想在家庭里使用这个软件，这也是
> 我最初设定它的初衷。我希望家庭成员能够利用自己的家庭网络，甚至在
> 未来 IPv6 全面铺开的情况下，能够利用家庭网络实现家庭设备的点对点
> 互联。所以我们必须有一个功能，就是能够在某一台机器上启动为所谓的
> "中枢"吧。

## 裁决

### [H1] 接入方式：朴素可靠优先，mDNS 不是核心

> mDNS 只是一个上层的"发现"，具体握手互联，仍然基于 opendweb 的
> 协议。所以你说的基于二维码、手动输入等方式，仍然是最朴素可靠的
> 方案。

**解读边界**：成员设备找到中枢的基线 = 二维码/短码/手动地址传递（承载
地址与引导信息；身份与准入仍走 opendweb 既有协议——邀请码/敲门）。
mDNS 类自动发现不作为本 change 的核心承诺（可作为后续可选增强）。

### [H2] 中枢托管形态：托盘做成插件，`opendweb tray` 启动

Owner 选择（2026-09-23 补充裁决）：**opentray 是可选的，做成插件，
`opendweb tray` 来启动**——托盘常驻进程管理中枢（图标状态：运行/
敲门待处理/异常；起停与开机自启；点开即管理台 webui），以 opendweb
既有 plugin 体系交付（与 `opendweb webui` 同模式：插件包可经
marketplace 安装，未安装不影响核心功能）。

**边界**：托盘壳 = opendweb 插件包（本 change 或配套插件仓库交付），
不硬依赖 opentray 主产品；中枢核心（守护/生命周期/契约）不依赖插件
存在——插件是体验层，核心面 CLI 直达。

### [H4] webui 双形态：既是 plugin，也是可复用 SDK（2026-09-23，Owner）

> 所以 tray 插件本身依赖了 webui 插件，那么意味着 webui 本身既要是
> 一个 plugin，也要是一个可复用的 SDK。

**解读**：`packages/webui` 分层为——
- **核心 = 可嵌入 SDK**：sidecar 运行时（node:http 零依赖，进程内可
  起停）、节点簿/状态逻辑、SPA 资源解析、类型化事件与配置面——
  具备编程消费入口（`startSidecar` 一族），供 tray 插件等宿主进程内
  复用（避免插件套子进程的双层进程树与 nodes.json 并发宿主）；
- **壳 = plugin 适配器与 CLI**：`opendweb webui` 走 marketplace 插件
  分发（既有形态不变），CLI 直达——两者都是 SDK 之上的薄壳。

托盘唤起 webui（含深链到敲门台等页面）经 SDK 进程内完成；独立使用
webui 的用户体感不变。SDK 面（配置/事件/生命周期/资源）冻结进 spec。

### [H3] 架构共识（对话确认，作为设计前提）

- **中枢 ≠ 流量瓶颈**：数据面点对点直连（局域网内现成；IPv6 直连为
  iroh 原生能力，铺开后自动受益）；中枢承担**寻址（rendezvous）+
  回退（relay）+ 门禁（三角色）**。
- **不默认启动**（前一轮裁决沿用）：中枢是显式选择的一等本地服务，
  不在每台设备默认常驻。
- 复用既有能力：server 二进制已随每个 `opendweb` CLI 捆带
  （`opendweb server`），三角色准入/邀请码/webui/节点簿（server-access-roles
  交付）全部是中枢的现成部件——本 change 是家庭场景的包装与生命周期
  补全，不是新内核。
