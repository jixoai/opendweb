# Proposal: home-hub（家庭中枢）

## Why

**产品的最初场景（家庭）缺少"中枢"这个一等入口。** [H0 初衷]

现状离家庭故事差三层包装（内核已齐）：

1. **中枢没有"模式"**：`opendweb server` 是裸基础设施命令——家庭用户
   需要的是"把这台常开机器一键变成家里的中枢"：restricted 门禁开箱、
   admin token 本地安全落地、家庭化默认端口、防火墙/健康自检引导。
2. **成员接入靠口口相传**：中枢地址+凭证没有朴素可靠的传递形态
   （二维码/短码/手动输入是 Owner 裁决的基线 [H1]）；成员拿到后的
   接入闭环（邀请码 join / 敲门）已由 server-access-roles 交付。
3. **没有生命周期托管**：中枢应常驻（开机自启、状态可见、异常可察），
   Owner 裁定由 opentray 托盘集成 [H2]——opendweb 侧需交付托盘可消费
   的守护/状态/控制契约。

数据面不受影响：成员间点对点直连（局域网现成、IPv6 原生），中枢只做
寻址+回退+门禁 [H3]——本 change 不触碰内核转发路径。

## What Changes

### 中枢模式（CLI + 服务面）

- `opendweb hub init`（或等价形态，命名 PM 期定）：家庭化预设一键起
  中枢——restricted + 本地生成并安全保存 admin token + 固定家庭端口
  + 首次防火墙/端口可达性自检 + 接入引导（含二维码/短码承载的地址与
  凭证引导信息）。
- 守护生命周期：`--daemon` / `status` / `stop` + launchd/systemd
  用户级服务安装助手（跨平台包装，家庭设备重启后中枢自动回来）。

### 托盘插件（`opendweb tray`）

- 托盘做成 opendweb 插件（与 `opendweb webui` 同模式：插件包经
  marketplace 可装、可选、核心不依赖）[H2]：图标状态（运行/待处理
  敲门数/异常）、起停与开机自启、点开即 webui。
- 中枢核心（守护/生命周期/状态面）CLI 直达；插件消费同一状态/控制
  契约——契约冻结于 spec，供插件与未来其它宿主复用。

### 成员接入

- 接入信息卡片：中枢地址 + 引导（二维码/短码/手动地址三形态 [H1]），
  承接既有邀请码/敲门流（不新建准入机制）。

## 非 Goals（明确不做）

- mDNS/局域网自动发现（[H1]：非核心；后续可选增强另立 change）
- 默认启动/每设备常驻（[H3]）
- 中枢侧转发/路由/存储功能（数据面 P2P 直连，中枢非瓶颈）
- opentray 壳本体实现（本仓库只交付其消费的契约）

## 依赖与基线

- 叠在 server-access-roles 之上（三角色/邀请码/webui/节点簿为其交付）
- `@jixo/opendweb-server-binary`（server 二进制捆带）与 webui sidecar
  均为现成部件
