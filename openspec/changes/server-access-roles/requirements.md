> 引用处标注 [R1]-[R8]。

## 心智模型（Owner 原话）

> 从三个角色出发，就是 包租婆、租户、访客。
>
> 首先，Opendweb 它本身是一个开发工具包。所以理论上应该是由对应的客户端去负责连接行为。这也是一开始我跟你聊的设计，就是提供 SDK，然后让客户端去引导用户做相应的配置。
>
> 但这就会导致管理相对混乱。但大部分情况下是不需要管理的。但如果有，那么事情会变得更清晰。我可以从蓝牙设备这个角度来引导你认知这个理念。
>
> 很多软件它自身是提供蓝牙设备的连接管理能力的。
> > 这就好比 opendweb 可以用在很多产品上，这些产品可以自己部署 opendweb 服务器，然后这些产品可能是有中心化的账号体系，然后基于这些账号体系关联客户的设备公钥、等级、余额等信息，从而实现只需要登录账号，就能通过服务器 p2p 连接服务器上的其它用户。
>
> 同时，操作系统仍然给出了统一的蓝牙设备管理界面，你可以在这边主动连接或者是断开。
> 所以我们需要做的是一台设备，一个 key。准确说是一个默认 key（不排除用户可以自己其它密钥对，这属于高级功能，属于是切换设备指纹的概念）。
>
> 包租婆的概念就意味着它拥有这栋房子（这台服务器），那么就意味着它可以给别人开号（租户），并且给别人配置权限。这里可以围绕 key 这个概念展开（其实我更加建议在 key 里面混入一些元数据，比如客户可以自己定义自己的 alias，方便识别管理，但是这种方便可能伴随风险，因为蓝牙、WiFi 就经常利用这种机制，导致钓鱼事件。但是我们不能否认，这个机制在大部分场景下它都是有易用性的价值。但是我们可以结合区块链钱包的做法，我们可以在 别名 后面带上一个括号：基于 public-key 计算出一个地址然后用 xxx***xxx 作为缩写减少误判）。
>
> 我们回到开号这个场景下，它有两种可能：一种是我已经拿到公钥了，那么我直接导入，将它配置成"访问者"（访客）或者"拥有者"（租户）。
> 如果是拥有者（租户），意味着它在这台服务器上有一个自己的"房间"，别人可以根据门牌号找到它。
> 如果是访问者（访客），意味着它可以访问链接这台服务器上的租户。
> 这里我们还可以做策略，比如让任何人默认都是"访问者"。也可以做黑名单白名单的功能。
> 我举例子，假设访客 X 来找租户 Y，有三种基础：
> 1. 完全放行制度：直接让 X 和 Y 对接，就是直接把 X 送到 Y 房间里面
> 2. 租户黑白名单制度：只把 X 送到 Y 门口，让 Y 自己决定要不要接纳 X。也就是说 Y 需要处理访问请求，那么意味着 Y 可以自己建立黑白名单。
> 3. 包租婆黑白名单制度：包租婆直接自己基于自己的黑白名单来限制 X 是否可以进出。
> 4. 还有就是 3+2，但这不是基础方案，属于混合方案，等于有两个门槛。
>
> 也就是说，如果我是服务器的管理员，我可以开启黑白名单；如果我是租户，我也可以开启黑白名单。

## 节点管理裁决 [R7]

> 首先，确实需要管理多台节点的能力。但是，你目前的设计其实更正确一点：在右上角有一个节点信息，我们直接在那边做切换就好了，并不需要在界面上同时实现多个节点的管理。这边只需要专注于配置一台节点就好。

## 拍板问答（2026-09-22）

**访客默认准入策略 [R3/R4/R5]**：

> 动态 callback，我们自己有 webui，那么就意味着有一个管理员（包租婆）可以去决定如何放行，那么管理员可以在界面上看到访客请求，就可以决定给这个 key 定位成 访客 还是 租客。甚至还有一种可能，包租婆直接提供一个"租户邀请码"，并限制这个"租户邀请码"默认只能使用 1 次，并且有默认 7 天过期时间（可以自定义 times+deadline）。从而就可以实现租户自己输入邀请码来实现注册成租户的功能。对了，我们也需要为租客提供一个过期时间（默认 deadline：今天+30 天 后过期）的配置。这些配置都是目前 opendweb 管理内核需要补充的。因为非常常用。

**门牌号发现 [R1]**：

> 只能说邀请发现的画面是对的，但本质上不是邀请，是把公钥给到访客，访客就能自己找上门。所以如果我已经有公钥，那么理论上不用邀请这一步就能访问到。如果是一个软件平台，那么我用这个平台的 id 找人的功能，找到这个人后，得到它的 id，那么理论上就能去做敲门访问了。

**本轮范围**：全量一次做（内核协议 + webui 三角色重设计 + 节点簿切换，完整 PM+Codex 闭环）。
