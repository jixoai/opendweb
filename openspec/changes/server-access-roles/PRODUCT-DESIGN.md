## 1. 产品定义演进

### 1.1 一句产品定义

**v1**：webui-console 是 Owner 的「服务器驾驶舱」——安全地回答「我的 dweb-server 还正常吗、谁在用它、谁能用它」，并在需要时收回访问。

**演进后**：webui-console 是一栋楼的三角色管理台——安全地回答「我的楼正常吗、楼里有什么人、多少租户多少访客、有没有人在敲门」，并决定**谁能进、谁该走、谁永远别来**。

三个关键定位裁决（v1 全部延续，语义升级）：

1. **它仍然是管理面，不是数据面。** 一切动词仍是管理动词（定位、签发、续期、拉黑、断开）。三角色模型把管理对象从「一个所有者名册」扩展为一族名册（租户/访客/黑名单）+ 一个待办（敲门台）+ 一叠凭证（邀请码），但不引入任何「使用网络」的动词。
2. **它仍然是本地可信终端。** 节点簿 [R7] 让你能管理多台楼，凭证边界不变：token 只进本地 sidecar 进程、不进浏览器。这是节点切换叙事里必须反复确认的信任事实（§4.4）。
3. **频率分布演进为：看 >> 处置 >> 开号 >> 配。** v1 的「看 >> 管 >> 配」加入了一个新的高频高压动作族：敲门处置——事件驱动、对方在线等，时效性高于一切例行管理。敲门台的「待处理」必须出现在总览首屏（§3.4）。

### 1.2 角色模型（Owner 心智的规范表述）

| 角色 | 是什么 | 在这台服务器上能做什么 | 界面在哪 |
|---|---|---|---|
| **包租婆（你）** | 拥有这栋楼（服务器）的人：开号、配权、封禁 | 本控制台的全部管理动作 | 本控制台（ready 世界） |
| **租户** | 在楼里有自己房间的一个 Fabric 网络：有门牌、可签通行票给自己的成员 [R1] | 连接组网；被发现（resolve）；发通行票；**房间内部事务（房门制）由 Fabric 自身成员名单承担，本轮不改**（proposal 非 Goals） | 无管理面登录；经邀请码/敲门台/名册「经过」本控制台 |
| **访客** | 有楼内通行权的设备（一个公钥）[R1][R3]：进得了楼、没自己的房间 | 连接；查找门牌（resolve）；**不能登记门牌（announce）、不能签票** | 同上；在访客名册与在线连接页呈现 |

辅助概念（在 UI 首现处各定义一次，进 §5 术语表）：

- **楼门**（服务器准入）：租户名册 + 访客名册 + 黑名单共同构成的大门。开放模式下楼门不上锁（三角色面降级，见 §3.5）。
- **房门**（Fabric 准入）：租户房间内部的成员门控。本轮为解释性呈现，Phase 2（proposal 非 Goals：fabric wire 变更不做）。
- **通行票**（capability）：租户发给自己的成员的票。包租婆不签票（server spec：server.key MUST NOT 签发 capability）；访客没有票也能进楼（无票名册，proposal）。
- **设备 key**：一台设备一个默认 key，key 即设备身份（relay 握手已密码学认证端点，设备 key 就是身份）[R1][R2]。多密钥对（切换设备指纹）为高级功能，本轮仅文档化、不进 UI [R2]。

身份对应（server spec 的 Admin ≠ Owner 区分如何融入）：**Server Admin = 包租婆 = 控制台使用者（「你」）；Relay Owner（registry 条目）= 租户。** v1 §8.3 的消歧纪律全部延续：UI 不用「管理员」指代使用者，admin token 一律称「管理凭证」；「包租婆」作为 Owner 给定的教育比喻，只出现在引导、术语解释与帮助文案中，不进导航与操作文案。

### 1.3 Jobs-to-be-Done（三角色，各按频率排序）

**包租婆（控制台使用者）**

| # | Job | 频率 | 完成判定 |
|---|-----|------|----------|
| P1 | **巡检升级**：楼正常吗 / 谁在楼里 / 几个租户几个访客 / 有没有人敲门 | 每次打开 | 总览首屏 3 秒、不滚动不点击四问全答（v1 三问的扩展） |
| P2 | **敲门处置** [R3]：有人敲门时看到请求，当场定位成访客或租户（或拉黑/忽略） | 事件驱动、对方在等 | 从总览待办条进敲门台，一次操作完成定位；对方重连即通 |
| P3 | **开号与续租** [R4][R5]：签发邀请码、手工导入公钥、续期/改期/设永久 | 中低频（成员变化/租期节点） | 名册反映意图；到期日与剩余时长可见；续期有名册版本+1 回执 |
| P4 | **门禁与封禁** [R8]：维护黑名单，确信被拉黑者同票也进不来 | 低频高压 | 拉黑后敲门台不再出现该端点、连接被拒且有用户话术 |
| P5 | **换楼** [R7]：在多台服务器之间切换 | 低频 | 顶栏节点簿完成切换，页面几秒重连，两楼门禁互不影响 |

**租户（fabric 所有者，无控制台登录——其 job 发生在客户端，管理台只承接结果）**

| # | Job | 频率 | 完成判定 |
|---|-----|------|----------|
| T1 | **注册进楼** [R4]：拿邀请码在客户端自助注册成租户 | 一生几次 | 兑换成功即组网可用；包租婆名册自动出现该租户（带别名提示/缩写/到期日） |
| T2 | **被找到** [R1]：门牌可被访客 resolve、自己的成员可组网 | 持续 | 不经过本控制台（fabric 内部）；在线连接页可见其流量投影 |
| T3 | **续租** [R5]：到期前知道要续、推动包租婆完成续期 | 每租期一次 | 客户端在临期/到期时收到明确话术（§5.3）；续期由包租婆执行 |
| T4 | **管理房门**（自己的访客政策）[R8] | — | 本轮由 fabric 成员名单承担，无独立 UI（Phase 2 / owner-console） |

**访客（楼内通行权，无房间）**

| # | Job | 频率 | 完成判定 |
|---|-----|------|----------|
| V1 | **敲门进楼** [R1][R3]：拿到楼的存在（服务器地址）后敲门，等待放行 | 每次首次接入 | 被拒时客户端话术指明「敲门已送达、等待放行」；包租婆定位后重连即通 |
| V2 | **找人** [R1]：按门牌（公钥）找到租户并连接 | 每次使用 | resolve 命中、组网成功 |
| V3 | **明白被拒**：过期/被拉黑时得到人话与出路 | 异常时 | 客户端呈现 §5.3 映射文案，知道该找谁、下一步做什么 |

### 1.4 产品模型增量（对象树演进，接续 v1 §1.4）

```
对象模型（Entity / Ownership / Lifecycle / State）：

  节点簿（sidecar 本地保存的多台服务器；0..1 台「当前节点」）
    └─ 当前节点（Server，激活期内冻结；切换 = sidecar 重启指向 [R7]）
         ├─ 租户名册（N 条：(fabric, 根端点) + 别名 + 到期时间 [R4][R5][R6]）
         │     生命周期：邀请码兑换/手工导入 → 在租 → 临期(≤7天) → 已到期(新连接被拒，可续期)
         │     → 注销（退租，条目移除）    每次变更 ⇒ 名册版本 +1 + 签名回执
         ├─ 访客名册（N 条：端点公钥 + 别名 + 授予时间；进楼权，无房间）
         ├─ 黑名单（端点/Fabric 两维度；先于一切准入判定 [R8]）
         ├─ 敲门台（未处置的敲门事件，按端点聚合；处置四动作消耗：定位访客/
         │     导入租户/拉黑/忽略——其中「忽略」不改变门禁）
         ├─ 邀请码（签发 → 待使用 → 已用尽/已过期/已吊销；服务端只存码指纹）
         └─ 在线连接（per 租户 × per 访客 × per 端点投影；断连闭环同 v1）

旅程映射（对象如何流经界面）：
  陌生人 --敲门--> 敲门台 --定位/导入--> 访客名册 | 租户名册
       --滥用--> 黑名单（同票也进不来 [R8]）
  租户 --到期--> 名册红标（新连接被拒） --续期--> 恢复在租
  邀请码 --兑换--> 租户名册新条目（自助通道 [R4]）
  节点簿：切换当前节点，以上所有对象随节点整体切换、互不影响
```

关键对象裁决：**「所有者」名册更名并扩展为「租户」名册**（同一对象：registry 二元组不变，加 别名/到期 [R5][R6]）。这不是新对象而是生命周期扩展——v1 的名册版本/回执/注销语义全部继承。

### 1.5 术语迁移（需 Owner 拍板）

v1 §8 拍板「Owner 译作所有者」。本轮 Owner 裁决原文通篇使用**租户/租客/包租婆**（requirements.md 心智模型），且裁决索引正式定名「租户邀请码」「租户过期」[R4][R5]。故呈请裁决：**呈现层「所有者」全部更名为「租户」**，工程字段（owner/owners/registry 等）为冻结契约不动，仅 UI 呈现层中文更名。本文以下一律使用「租户」。存量用户的教育以首现处定义句承担（§5.1），不做迁移弹窗。

## 2. 使用叙事（五个，步骤级）

### 叙事 N1：陌生人敲门（对应 P2/V1，[R3]）

1. 张三从同事那里拿到这栋楼的地址（服务器 URL），在自己设备的客户端里连上去。
2. 门禁拦下他（`dweb/no-capability`）。客户端不重试轰炸，明确提示：「门禁不认识这个设备。你的敲门已送达管理者，等待放行后重新连接即可进楼。」（§5.3）
3. 你（包租婆）打开控制台。总览健康结论下方出现一条待办行动条：「**有 1 台设备在敲门**——去处理」，侧栏「访客与门禁」同时亮起徽章。
4. 点进行敲门台：一行聚合记录显示端点缩写 `a1b3***f02c`、最近敲门时间、累计 3 次、原因「陌生设备，无通行票」。
5. 你线下核对身份（让张三报公钥尾号），确认是本人。
6. 点「定位为访客」，确认对话写明后果（能进楼、没房间、长期有效直到移出）；确认后该行离场，就地提示：「已定位为访客。对方重连即可进楼。」
7. 张三点重连，进楼；在线连接页出现该端点，角色标记「访客」。他 resolve 到要找的门牌，组网开始。全程你没看过任何文档。

### 叙事 N2：签发邀请码，租户自助入驻（对应 P3/T1，[R4][R5]）

1. 李四团队要入驻。你在「租户管理 → 邀请码」点「签发邀请码」。
2. 表单默认：可用次数 1、有效期 7 天 [R4]；你填别名提示「李四团队」，确认。
3. 完整码**一次性**展示（大字等宽 + 复制），旁注「此码只显示这一次；服务器只保存码的指纹」。你复制发给李四。
4. 李四在自己客户端完成注册：客户端引导他先确保有自己的 Fabric（根节点就绪），然后粘贴邀请码提交（码 + 自己的 fabric + 根端点，走公开兑换端点，见 proposal）。
5. 服务端校验通过（码未用尽、未过期），写入租户名册：二元组 + 别名预填「李四团队」 + 到期日 = 今天 + 30 天 [R5]。
6. 你的名册自动多出一行：`李四团队 (ab12***cd34)`，状态「在租 · 剩 30 天」；码状态翻为「已用尽」，再拿同码注册被拒。
7. 李四的设备从此可被 resolve 找到、可给自己的成员签通行票。两边零线下传递密钥原文。

### 叙事 N3：租期到期的运营节奏（对应 P3/T3，[R5]）

1. 距某租户到期还有 5 天：总览「租户」卡副行出现黄色提示「1 个租户 7 天内到期」；名册该行黄标「还剩 5 天」。
2. 你提醒李四，李四确认续租。你在名册行点「续期」：弹窗展示当前到期时间，选项「+30 天 / 自定义日期 / 设为永久」，确认后有回执（名册版本+1），黄标消失。
3. 没续上：到期日之后，该租户的新连接被拒，李四客户端看到「租期已到：该网络的租期已结束，请联系管理者续期」（§5.3）；名册行红标「已到期」——**条目还在，随时可续**，这是「到期 ≠ 退租」的关键语义。
4. 你随后补续期，李四重连即恢复，无需重新注册、别名与门牌不变。

### 叙事 N4：滥用者进黑名单（对应 P4，[R8]）

1. 某端点连续异常敲门（敲门台该行计数飙高），或你从在线连接观察到滥用。
2. 敲门台该行点「拉黑」，确认对话写明强度：「此后它的敲门不再出现在敲门台，**即使它拿到有效通行票也无法接入**。黑名单在一切准入判定之前生效。」确认。
3. 该端点（及其全部历史敲门记录）从敲门台消失；它再敲门静默丢弃，不再打扰你。
4. 它设法搞到一张有效通行票，仍被拒（`dweb/blocked`），客户端话术「已被列入黑名单」（§5.3）——同票也进不来。
5. 若是误判，你在黑名单里移出它，它回到「敲门可见」状态，可重新走放行流程。

### 叙事 N5：切换节点（对应 P5，[R7]）

1. 你管两台服务器：公司一台、家里一台。顶栏右侧的节点按钮始终显示**当前节点**的掩码地址。
2. 点开节点簿：当前节点详情在上（掩码地址、安全模型），已保存节点列表在下。
3. 选另一台，切换确认写明：「切换会重启本地后台进程并指向新节点，页面将短暂重连（通常几秒）。已保存的管理凭证只存在本地进程，不会离开你的电脑；**两个节点的门禁互不影响——你在这边拉的黑，不会挡住另一边的敲门**。」
4. 确认后页面短暂「正在连接服务器…」，健康灯恢复，全站数据整体切换为新节点的（名册、敲门台、在线都是新楼的）。
5. 添加第三台：在节点簿底部走一次紧凑配对（地址 + 管理凭证 + 配对码）「连接并保存」；删除一台：确认「只删除本地保存的配置，不影响那台服务器」。

## 3. 信息架构演进

### 3.1 为什么「访问管理」要拆（演进理由，不推翻 v1 问 3）

v1 问 3 合并 owners+connections 的依据是：「谁能用 / 谁在用是**同一对象**的两态」。三角色模型使这个前提不再成立——准入对象分裂为三个对象族（租户：有房间者的名册+到期+邀请码；访客：通行者名册；黑名单：禁止名单），各自有不同的属性、生命周期与动作集；在线连接的主体也扩展为租户+访客两族。若仍塞进一页，将是五张表平级陈列（名册/邀请码/敲门/访客/黑名单），重演 v1 诊断的「平级卡片」病（v1 §2.2 IA-1）。

因此按**对象族**拆分：名册类（租户）一页、门禁类（敲门台+访客+黑名单）一页、在线独立一页。这是 v1 原则（按管理者任务组织，不按 API 端点组织）在新对象模型上的再应用，不是对 v1 问 3 的否定——v1 建立的名册⇄在线互链（RosterView 行内「在用/未在用」→ OnlineView 按 Fabric 过滤，现状代码已实现）原样保留。

各页信息层级：

- **总览**：健康结论区 →（有待处理敲门时的）待办行动条 → 关键数字四卡 → 配置投影 → 空楼引导（§3.4）。

### 3.4 总览升级：三问变四问

首屏不滚动、不点击，3 秒回答：

1. **楼正常吗**——健康结论区（v1 原样，四态健康灯语义不变）。
2. **有没有人敲门**——有未处置敲门时，健康结论正下方出现待办行动条（v1 四级层级中新增的一级，仅在有待办时占据）。
3. **楼里有什么人**——关键数字卡。
4. **几个租户几个访客**——关键数字卡（租户卡副行承载临期预警）。

关键数字四卡演进（v1：在线/所有者/模式/名册版本）：

- **在线连接 N 条**（按端点 N 个；点击下钻在线连接页，v1 保留）
- **租户 N 个**，副行：「其中 n 个 7 天内到期」（黄字，有点击进名册过滤临期；无临期时副行为「名册内可接入的 Fabric」）
- **访客 N 个**，副行：「可进楼、无房间」
- **接入模式**徽章（v1 保留；受限模式悬停语更新为「租户与访客可进，陌生人敲门待放行」）

名册版本从数字卡降级进配置投影区（v1 已裁「配置投影低视觉权重」；数字卡位让给访客）。配置投影区新增一行「房门制：各租户房间内部自管（Phase 2 前由 Fabric 成员名单承担）」。

### 3.5 房门三制在本轮的呈现边界 [R8]

Owner 的三制（完全放行 / 租户名单 / 包租婆名单 + 混合）中：

- **包租婆名单制**：本轮完整落地——访客名册（放行半边）+ 黑名单（拒绝半边）= 楼门。访客与门禁页即它的操作面。
- **租户名单制**：本轮由既有 Fabric 成员门控承担（proposal 非 Goals），UI 只做解释性呈现（访客与门禁页底部说明卡，文案见 §5.4）。
- **完全放行制（房门侧）与混合制（两个门槛）**：Phase 2，UI 不呈现控件、不虚构状态。

开放模式（mode=open）：楼门不上锁，三角色面大部分失效。门禁页呈现整页解释态（同 v1 在线页开放模式空态的处理模式）：「这台服务器处于开放模式——任何人都能进楼，敲门台与门禁不生效。切换到受限模式后，这里才会开始记录敲门。」（开放模式下黑名单是否仍生效，列为开放问题 O-9。）

## 4. 关键交互流（步骤 + 成品中文文案）

### 4.1 流 A：敲门台处置（四动作）[R3][R8]

敲门台数据形态：按端点聚合的待处理队列（端点缩写 / 最近敲门时间 / 累计次数 / 敲门原因），最新在上；行内展开动作。同一端点多次敲门聚合一行，避免刷屏（推断：依据 proposal「内存台账 + 有界容量」与 per-source 频控，聚合是呈现层必需——证据等级：PM 判断，待可用性验证）。

| 步 | 界面行为 | 成品文案 |
|---|---|---|
| 1 | 总览待办条 / 侧栏徽章点击 → 进入敲门台 | 页题：**访客与门禁**；敲门台卡题：**敲门台**，副注：陌生设备尝试连接这台服务器时，请求会出现在这里，等你放行或拒绝。 |
| 2 | 行展开显示完整身份与四动作 | 端点 `a1b3***f02c` · 最近敲门 14:02 · 累计 3 次 · 原因：**陌生设备，无通行票**<br>动作：**定位为访客** / **导入为租户** / **拉黑** / **忽略** |
| 3a | 「定位为访客」确认（知情前置：权限范围+无房间+期限+撤销路径） | 标题：**让这个设备进楼？**<br>正文：将把端点 `a1b3***f02c` 加入访客名册。加入后，这个设备可以连接这台服务器、查找租户的门牌，但**没有自己的房间、不能被别人找到**。访客身份长期有效，直到你把它移出名单。<br>按钮：**定位为访客** / **先不了** |
| 3b | 「导入为租户」确认（表单：根端点预填敲门端点、可改；Fabric 必填） | 标题：**把这个设备导入为租户？**<br>表单：根端点（预填 `a1b3***f02c` 对应全文，可修改）/ Fabric（64 位十六进制，需补填）<br>警示：请先核对根端点缩写与敲门端点一致再导入。<br>正文：导入后它在这台服务器上拥有自己的房间，别人可以按门牌找到它；默认租期 30 天，可随时续期或设为永久。<br>提示：不知道它的 Fabric？改用邀请码，让对方在自己客户端完成注册。<br>按钮：**导入为租户** / **先不了** |
| 3c | 「拉黑」确认（强度披露：同票也进不来） | 标题：**把这个设备拉黑？**<br>正文：将把端点 `a1b3***f02c` 加入黑名单。此后它的敲门不再出现在敲门台；**即使它拿到有效通行票，也无法接入**。黑名单在一切准入判定之前生效；移出名单前，这个设备与本服务器彻底无缘。<br>按钮：**确认拉黑** / **先不了** |
| 3d | 「忽略」**不弹确认**（低后果，保留控制感用 toast+可逆） | 行直接离场，toast：**已忽略。门禁没有变化——它下次敲门还会出现在这里。** 附动作链接：**拉黑它** |
| 4 | 处置成功反馈（就地，行离场） | 定位成功：**已定位为访客。对方重连即可进楼。**（附：告诉对方现在可以重连）<br>导入成功：**已导入为租户。去名册设置别名与租期。**（点击跳名册该行）<br>拉黑成功：**已拉黑。它的敲门不会再出现。** |
| 5 | 空态 | **现在没有人在敲门。**<br>有陌生设备尝试连接时，请求会出现在这里，等你放行或拒绝。 |

敲门原因列的呈现映射（管理者侧）：无票且不在任何名册 →「陌生设备，无通行票」；票无效/过期 →「通行票无效」；租户已到期 →「所属租户租期已到」。客户端侧用户话术见 §5.3（两侧文案不同受众、同一事实）。

> **这栋楼有两道门。**
> 楼门（本页）：由你决定谁能进——租户名册、访客名册与黑名单。
> 房门（各租户房间）：租户在自己网络内部的成员名单，由租户自管；「访客到了租户门口，租户开不开门」属于房门规则，当前由 Fabric 成员门控承担，本控制台暂不提供租户侧门禁配置。

## 6. 设计方向增补（B 台账基座上的新面气质约定）

不新开方向。方向 B（Stripe 式台账：左侧导航 + 内容区、中性蓝灰、语义色克制、中等密度、可审计感）已验收，以下仅约定三角色新增面的**密度与组件气质**，供视觉执行方直接消费：

- **敲门台 = 待办队列气质（inbox / triage）**：不是聊天流，不是日志表——是收件箱。待处理行有轻量优先级视觉（时间越近越上、累计次数徽章）；动作在行内触达（一次点击达确认）；处置即离场（行的消失就是反馈）；空态安静。参照 GitHub notifications / Linear inbox 的分诊节奏：扫一眼 → 逐条裁决 → 清空离场。
- **邀请码 = 凭证管理气质（credentials）**：签发即掩码、完整码仅一次性展示、状态徽章四态（待使用/已用尽/已过期/已吊销）、吊销为一等动作。参照 Stripe / Vercel 的 API Keys 页：克制、等宽、无装饰，凭证的「一次性可见」是页面的仪式感来源。
- **名册 = 台账表格气质（B 基座延续）**：密度中高、等宽数字对齐、状态列用色克制（临期黄、到期红、在线绿点——语义色只进状态，不做整行染色）；时间人类可读 + 剩余天数并列。
- **节点簿 = 切换器气质（switcher）**：弹层承载，绝不占侧栏；当前节点是锚点信息，切换动作带短暂全屏过渡（复用 bootLoading 形态），安全披露文案在确认内而非事后。
- **总览待办条 = 行动号召，非常驻装饰**：无敲门时完全不存在，有敲门时是健康结论后的第一视觉落点；颜色用警示级但不闪动、不动画循环。
- 红线自检（anti-patterns，延续 v1）：无渐变、无发光、无玻璃拟态；语义色仅用于状态结论；徽章不堆叠（一行至多一个状态徽章 + 一个计数徽章）。

## 7. 验收标准（小白可检验）

结构验收：

1. **敲门闭环零文档**：找一位没读过文档的人用陌生设备连接服务器——设备端看到「敲门已送达、等待放行」；操作者在总览首屏看到「有 1 台设备在敲门」；进敲门台一次点击完成「定位为访客」；设备重连即通，在线连接页出现且标记为访客。全程不看文档、≤3 分钟。
2. **邀请码自助注册**：按默认值（1 次/7 天）签发 → 租户在客户端兑换 → 名册自动出现该租户（别名提示 + 缩写 + 到期日 = 今天+30）→ 码状态变「已用尽」，同码再兑被拒并有话术。
3. **到期生效可观察**：将某租户到期设为临期 → 总览租户卡出现黄色预警；到期后其新连接被拒、客户端见「租期已到」、名册行红标；续期后重连即通、名册版本+1 有回执。
4. **黑名单生效可观察**：拉黑某端点后——它再敲门不出现在待处理；给它一张有效通行票仍被拒（客户端见「已被列入黑名单」）；黑名单里移出后恢复敲门可见。
5. **节点切换后凭证边界仍成立**：浏览器开发者工具的 storage 中全程无 token 痕迹；添加第二台节点并切换 → 页面数秒重连、健康灯恢复；A 楼拉黑的端点在 B 楼照常敲门可见（门禁互不影响）；删除节点不影响那台服务器。
6. **防钓鱼缩写**：两个不同公钥设置同一别名——界面可区分（缩写不同）；所有确认对话同时展示别名+缩写；同一密钥在敲门台/名册/在线/黑名单四处缩写一致。
7. **3 秒巡检保持**：总览首屏不滚动不点击，回答四问：楼正常吗 / 有没有人敲门 / 谁在楼里 / 几个租户几个访客。
8. **术语与契约回归**：呈现层全站无「所有者」残留（工程字段除外）；v1 全部冻结面（回执字段、断连四态、失败码矩阵、目标冻结、token 不回显）既有测试绿灯；「访客可 resolve、不可 announce」在门禁页解释与在线页呈现中无矛盾表述。

体验验收：

9. 按评审记分卡复评六维，平均 ≥ 8 且无核心维度 < 7；发布会截图测试：敲门台有待办时的「访客与门禁」页截图，Owner 判定可进产品文档。

## 8. 风险与开放问题（PM 无法裁决，需 Owner / Codex 定）

| # | 问题 | PM 建议（供裁决） |
|---|---|---|
| O-1 | **访客是否需要到期**：[R5] 只给租户定了到期；访客默认长期有效是否有风险 | 建议：访客默认长期（低权限低风险，房间与签票权都没有），名册保留「移出」即可；是否加可选到期看滥用面再议 |
| O-2 | **敲门记录保留时长**：proposal 定为内存有界台账（重启即清、容量有界）——「对方在等你放行」的时效承诺与重启丢失矛盾；最旧记录被挤掉时「待处理」计数失真 | 建议：产品上明示「敲门台是实时待办，不是审计日志」；容量与过期参数（如 24h / 1000 条）由 Codex 定并保证丢弃策略不静默改变待处理语义 |

| O-8 | **多管理员并发**：两个浏览器同看敲门台，处置归属与冲突（已处理记录的呈现） | 低优先级；建议先到先得 + 处置后另一端刷新即同步 |
| O-9 | **开放模式下黑名单是否生效**：open 模式无验证链，blocklist「先于一切判定」的语义是否覆盖 | 建议：产品呈现按「开放模式=门禁整体不生效」（§3.5），若技术侧可低成本让黑名单在 open 下仍生效则呈现需改，请 Codex 定 |
