# home-hub：家庭中枢（Owner 需求存档）

> 本文件逐字存档 Owner 的产品输入与裁决，是本 change 不可挑战的依据。
> 工程面解读与设计决策见 design.md（引用裁决编号 [H1]…[H3]）。

## 初衷（2026-09-23，Owner）

> 我之所以提到这个，是因为很多情况下我想在家庭里使用这个软件，这也是
> 我最初设定它的初衷。我希望家庭成员能够利用自己的家庭网络，甚至在
> 未来 IPv6 全面铺开的情况下，能够利用家庭网络实现家庭设备的点对点
> 互联。所以我们必须有一个功能，就是能够在某一台机器上启动为所谓的
> "中枢"吧。

## 裁决

### [H1] 接入方式：朴素可靠优先，mDNS 不是核心

> mDNS 只是一个上层的"发现"，具体握手互联，仍然基于 opendweb 的
> 协议。所以你说的基于二维码、手动输入等方式，仍然是最朴素可靠的
> 方案。

**解读边界**：成员设备找到中枢的基线 = 二维码/短码/手动地址传递（承载
地址与引导信息；身份与准入仍走 opendweb 既有协议——邀请码/敲门）。
mDNS 类自动发现不作为本 change 的核心承诺（可作为后续可选增强）。

### [H2] 中枢托管形态：托盘做成插件，`opendweb tray` 启动

Owner 选择（2026-09-23 补充裁决）：**opentray 是可选的，做成插件，
`opendweb tray` 来启动**——托盘常驻进程管理中枢（图标状态：运行/
敲门待处理/异常；起停与开机自启；点开即管理台 webui），以 opendweb
既有 plugin 体系交付（与 `opendweb webui` 同模式：插件包可经
marketplace 安装，未安装不影响核心功能）。

**边界**：托盘壳 = opendweb 插件包（本 change 或配套插件仓库交付），
不硬依赖 opentray 主产品；中枢核心（守护/生命周期/契约）不依赖插件
存在——插件是体验层，核心面 CLI 直达。

### [H4] webui 双形态：既是 plugin，也是可复用 SDK（2026-09-23，Owner）

> 所以 tray 插件本身依赖了 webui 插件，那么意味着 webui 本身既要是
> 一个 plugin，也要是一个可复用的 SDK。

**解读**：`packages/webui` 分层为——
- **核心 = 可嵌入 SDK**：sidecar 运行时（node:http 零依赖，进程内可
  起停）、节点簿/状态逻辑、SPA 资源解析、类型化事件与配置面——
  具备编程消费入口（`startSidecar` 一族），供 tray 插件等宿主进程内
  复用（避免插件套子进程的双层进程树与 nodes.json 并发宿主）；
- **壳 = plugin 适配器与 CLI**：`opendweb webui` 走 marketplace 插件
  分发（既有形态不变），CLI 直达——两者都是 SDK 之上的薄壳。

托盘唤起 webui（含深链到敲门台等页面）经 SDK 进程内完成；独立使用
webui 的用户体感不变。SDK 面（配置/事件/生命周期/资源）冻结进 spec。

### [H5] 三视角控制台：右上角=身份切换器（2026-09-23，Owner 走查反馈）

> webui 还有一个问题，它好像只考虑了包租婆角色，我之前提到过三种
> 角色。webui 需要分别适应这三种角色，右上角的入口非常重要：它应该
> 可以罗列出：我的服务器、我的服务商、我的到访。这三个名字有点
> 别扭，但差不多这个意思。这里的入口决定这节目（界面）应该如何渲染。

**解读**：控制台从"管理员管理台"升级为"这台设备的三张脸"——右上角
身份切换器决定全局渲染：我的服务器（包租婆，现有管理台）/ 我的
服务商（租户，本机 registration.json 账本：租约/倒计时/续期指引，
无 admin 面）/ 我的到访（访客，本机 visits 账本：放行后 best-effort
记录+连通探测）。命名 PM 轮打磨。托盘图标=三视角状态聚合。

### [H6] 默认别名=本机机器名（2026-09-23，Owner 走查反馈）

> 最大的问题就是，你没有把本地机器名默认作为别名来使用，我现在
> 看到的都是"c95***860"这样的"地址"，可读性很低。它更多是一种
> 身份识别。

**解读**：缩写是核验层（永远在，防钓鱼），机器名是称呼层（默认值）。
join 自报 hostname 为 alias（register 增量字段，自声明标签，管理员
可改）；`opendweb id` 增本机名；敲门者无自报通道（协议无载荷位），
敲门台仍缩写+管理员命名；访客签名自介=Phase 2 候选。

### [H3] 架构共识（对话确认，作为设计前提）

- **中枢 ≠ 流量瓶颈**：数据面点对点直连（局域网内现成；IPv6 直连为
  iroh 原生能力，铺开后自动受益）；中枢承担**寻址（rendezvous）+
  回退（relay）+ 门禁（三角色）**。
- **不默认启动**（前一轮裁决沿用）：中枢是显式选择的一等本地服务，
  不在每台设备默认常驻。
- 复用既有能力：server 二进制已随每个 `opendweb` CLI 捆带
  （`opendweb server`），三角色准入/邀请码/webui/节点簿（server-access-roles
  交付）全部是中枢的现成部件——本 change 是家庭场景的包装与生命周期
  补全，不是新内核。

### [H7] 三项拍板（2026-09-23，Owner：「没问题，这三步可以推进」）

1. **G-1 多租约进本 change 范围**：registration 从单条存储演进为
   0..N 租约簿——「我的租约」按账本设计交付（存储形态交 design.md）。
2. **O-1 三视角命名 = 组 B**：「我的中枢 / 我的租约 / 我的到访」。
3. **O-2 中枢命令 = 预设 A**：`opendweb hub` 命令族
   （init / start / stop / status / card / autostart），
   重看卡片子命令名 `hub card`。

**解读**：三视角控制台与 hub 命令族的命名基准全部落定，设计文档

### [H8] relay 凭证装配的 SDK 时序冲突修复路线（2026-09-23，Owner 拍板）

> 背景（Codex 设计评审 r8 唯一阻塞项）：SDK `createRoot/open` 构造期即
> `bind()` 并等 `endpoint.online()`（加载缓存票据并连 relay），早于调用方
> `ensureRelayCapabilities()`——「先签票后首拨」契约在构造期被打破。
>
> **Owner 拍板：选项 A——允许最小 SDK 扩展**（dweb-fabric 增生命周期 API：
> createRoot/open 可推迟 bind/online，调用方完成 ensure 与 tuple 断言后再
> 启动 Endpoint）。此前的「Rust 零产品改动」边界为编排方自定而非 Owner
> 裁决，本条修订为：**允许 dweb-fabric 最小生命周期扩展（含其配套测试）；
> dweb-server 仍零改动；G-3 用例仍 test-only**。
>
> **Owner 二次拍板（2026-09-23，r11 复审后）：[H8] 扩充**——除生命周期
> API 外，同时授权 **Roster 显式 fabricId 采纳**（`FabricOptions.fabricId`
> 仅 createRoot 生效：64hex 校验、roster 持久化采纳该值、既有随机行为
> 缺省不变、既有 roster 冲突=明确错误不静默改写）。身份语义改动的授权
> 范围以此为限；CLI 仍不引入 NAPI 依赖。

## 走查发现（2026-09-23 三角色 ego-browser 亲测，非裁决——设计吸收项）

全故事（包租婆 webui / 访客敲门 / 租户 join）跑通，[H6] 三断言全过；
两个服务端 bug（renew「顺延」基准、registered_at 改写）当日修复。
以下为体验层发现，home-hub webui 改造时吸收：

- **F1 名册外部变更不自动浮现**：对方说「join 好了」，包租婆名册
  >20s 不出现（手动刷新立现）——owners 列表轮询周期偏长或缺少变更
  推送；「配对成功」场景需要可感知的时效。
- **F2 在线连接「按端点」区易误读**：该区只投影租户，访客在线不进
  该表——同页「按访客」有 1 条在线时「按端点」显示「当前没有在线
  连接」，第一眼像矛盾；需说明性文案或视图归并。
- **F3 租户侧无剩余租期入口**：join 成功后 CLI 未指路如何查看剩余
  租期/状态（租约视角 [H5] 覆盖 webui 面；CLI 侧 status/hint 候选）。
- **F4 别名认知漂移**：包租婆可单方面改租户别名，租户侧无感知渠道
  （「我在对方名册里叫什么」不可见）；v1 接受，Phase 2 候选回执面。
- **F5 ego-browser 环境提醒**：Ego Lite 有更新（当前 0.5.0.32），
  走查代理按纪律未升级——升级与否由 Owner 决定。
